What You Learned

1. The three-layer naming system

The orchestrate CLI subcommands (toolkits, tools, agents) are fixed keywords built into IBM's ADK — they have nothing to do with your folder names. Your folder structure is just convention. The only name Orchestrate actually reads is the name: field inside your YAML file.

2. Two completely different tool patterns

FastMCP @mcp.tool (what you built)ADK @tool
Registered asToolkit (a process)Tool (a function)
How Orchestrate runs itStarts python server.py over stdioCalls the function directly
Import commandorchestrate toolkits importorchestrate tools import -k python
Good forGrouping tools, any Python librarySingle-purpose tools, simpler setup

3. How stdio transport works

Orchestrate starts python server.py as a subprocess and pipes JSON-RPC messages through its stdin/stdout. You never see a URL or port. The process is started by Orchestrate on demand — you don't run it yourself.

4. How package_root works

When you import a toolkit, Orchestrate uploads everything in package_root, runs pip install -r requirements.txt, then executes command. That's why the layout must be flat — no src/ nesting. Use an absolute path for package_root to avoid path-doubling bugs.

5. Token vs. API key — and why tokens expire

read -s WXO_API_KEY reads your key silently into memory. orchestrate env activate exchanges it for a short-lived session token stored on disk. unset WXO_API_KEY immediately erases it from memory. Tokens expire after a few hours — that's a security feature, not a bug.

6. The docstring IS the tool description

FastMCP reads your Python function's docstring at import time and reports it to Orchestrate via the MCP protocol. That's what fills the Description column in orchestrate tools list. Write clear docstrings — the LLM reads them to decide which tool to call.

7. The orchestrate chat ask EOF quirk

On SaaS, orchestrate chat ask opens an interactive session. When run non-interactively (from a script), it floods output with EOF when reading a line errors after delivering the response. The agent response above the EOF flood is real and correct — ignore everything below it.

What Real Work Looks Like From Here

The lab gave you three deliberately simple tools to prove the pipeline works end-to-end. Real hackathon work means replacing or extending those tools with something that solves an actual problem. The same architecture applies — you're just changing what the tools do.

The pattern that scales

  • One MCP server (server.py) groups tools that belong together — e.g., all tools for a specific data source or API
  • One agent per user-facing persona — it picks which tools to call based on the conversation
  • Multi-agent (collaborators) for complex workflows — a routing agent that delegates to specialist agents
  • Flows (@flow / ADK) for deterministic sequences — when you can draw a flowchart, use a flow instead of an agent

Questions worth answering before the next session

  • What data source or API do you want the next toolkit to wrap?
  • Is there a federal dataset, internal system, or external service you need to query?
  • What does a successful agent interaction look like — what question does a user ask, and what does a good answer look like?
